The RDBMS is the engine. SQL is how you talk to it.

A Relational Database Management System stores the tables, keeps the rules, and lets many users read and write at once without breaking anything.

Popular ones: PostgreSQL, MySQL, SQLite, SQL Server. We use PostgreSQL. It's what Supabase runs.

-- "Which tasks aren't done yet?"
SELECT title
FROM tasks
WHERE is_complete = false;

Four takeaways from the reading: data lives in tables, tables link through relationships, the RDBMS is the software that manages it, and you talk to it in SQL.

Table or column? Ask: does it have details of its own?

Its own table

  • project: has a name, a description, its own tasks
  • tag: has a name, and many tasks share it

Just a column

  • complete: yes or no
  • due date: one date
  • status: pending, in progress, done

If it's a single value, it's a column. If it has its own details, it's a table.

This is the tip box from the reading. "Status" is the classic trap: it feels like a thing, but it's just a value.

Every column gets a data type

INTEGER

Whole numbers. Seats at a table: 4, never 4.7.

BIGINT

Really big whole numbers. Page views.

NUMERIC

Exact decimals. Money: $19.99, exactly.

VARCHAR(n)

Short text with a limit. Usernames, emails.

TEXT

Text with no limit. Descriptions, comments.

BOOLEAN

true or false. A light switch.

DATE / TIMESTAMPTZ

A day / an exact moment, time zone aware.

UUID

A random, globally unique id.

The right type keeps bad data out. Never store money as FLOAT.

Three reasons types matter: data is stored correctly, invalid data can't sneak in, and the database can work efficiently.

FLOAT for money: 0.1 + 0.2 is 0.30000000000000004 in floating point. Fine for a game score, a real problem for a bank.

JSONB is in the reading too: a PostgreSQL "miscellaneous drawer" for JSON. Useful sometimes; don't use it to avoid designing tables.

UUIDs look like a1b2c3d4-e5f6-…. We'll use them for ids. They're safe to create anywhere without two ever colliding.

I'll call one out. You type its data type.

Answers:

  • price: NUMERIC(10,2), never FLOAT
  • is_published: BOOLEAN
  • birthday: DATE (no time of day)
  • bio: TEXT (no sensible limit)
  • email: VARCHAR(255). TEXT is also fine; Postgres people often prefer TEXT.
  • last_login: TIMESTAMPTZ (an exact moment)
  • seat_count: INTEGER

diagrams/DB1-03-relationships.tldr

Foreign key first: a column holding the primary key of a row in another table. tasks.project_id = 3 means "I belong to project 3". It's a pointer.

  • One-to-one: a person and their passport. users / user_profiles. The FK has UNIQUE on it so two profiles can't point at the same user. Rare.
  • Many-to-one: many employees, one company. The most common. The FK always lives on the "many" side: tasks holds project_id, projects doesn't list its tasks.
  • Many-to-many: students and courses. One FK column can only hold one value, so you need a third junction table. It can carry its own data: grade belongs to the pairing, not to the student or the course. Its primary key is often both FKs together (a composite key).

How to choose: say it both ways

SentenceAnswerWhere the FK goes
A task belongs to one project. A project has many tasks.many-to-oneon tasks (the many side)
A user has one profile. A profile belongs to one user.one-to-oneeither side, with UNIQUE
A task has many tags. A tag is on many tasks.many-to-manya junction table: task_tags

Don't reach for many-to-many unless both directions really are "many".

The decision process from the reading: write the relationship in plain English, both directions. One and many = many-to-one. One and one = one-to-one. Many and many = junction table.

"New designers make everything many-to-many. Before you add a junction table, ask: is there a real case with multiple records on BOTH sides?"
